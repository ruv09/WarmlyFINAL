# Адаптивная раскладка

Что должно корректно выглядеть: iPhone SE, iPhone 13 mini, iPhone 16 Pro
Max, обычные Android-телефоны, большие Android-устройства, планшеты
(базовая поддержка).

## Компоненты системы

```
src/constants/layout.ts       Брейкпоинты и классификация устройств по ширине
src/constants/spacing.ts      Шкала отступов + адаптивный множитель
src/constants/typography.ts   Размеры шрифта + лимиты масштабирования
src/hooks/useDeviceMetrics.ts Единая точка чтения размеров экрана
src/hooks/useAppTheme.ts      Тема + отступы, уже адаптированные под устройство
src/components/layout/Screen.tsx     Safe area, без фиксированных высот
src/components/layout/Container.tsx  Ограничение ширины контента на планшетах
```

## Решения и почему

### Классификация устройств — по ширине, не по названию модели

`getWindowSizeClass` / `getPhoneWidthClass` смотрят на фактическую
ширину экрана в dp, а не на список "если iPhone SE, то...". Это
единственный подход, который не превращается в нескончаемый список
частных случаев при выходе новых устройств — новый iPhone 17 или
новый Android-флагман просто попадёт в существующий брейкпоинт без
единой правки кода.

Внешний уровень — три класса `compact` / `medium` / `expanded`,
позаимствованные у Material 3 window size classes: это не
самодельная классификация, а проверенный отраслевой стандарт,
который одинаково хорошо описывает и iOS, и Android, и заодно уже
готов к альбомной ориентации (широкий телефон в landscape и
маленький планшет в portrait закономерно попадают в один класс
`medium` и получают одинаковое поведение).

Внутри `compact` (телефоны) есть более тонкая подшкала `narrow /
standard / wide`, потому что разброс ширины *внутри одних только
телефонов* (375dp у SE и 13 mini против 430dp у 16 Pro Max) — это уже
+15% пространства, которое стоит использовать для чуть более
просторной раскладки, а не оставлять как есть.

### Отступы — именованная шкала, а не константы по всему коду

`SPACING.md`, `SPACING.lg` и т.д. вместо `padding: 16` россыпью по
файлам. Причины:
- при пересмотре дизайна плотность меняется в одном файле;
- в коде видно *назначение* отступа (`md` — стандартный отступ блока),
  а не только число;
- шкала кратна базовой единице 4dp — предсказуемая визуальная сетка.

Множитель шкалы (`resolveSpacingMultiplier`) чуть сжимает отступы на
узких телефонах и чуть расширяет на планшетах — так одна и та же
семантическая шкала (`md` — это всегда "стандартный отступ блока")
даёт разный физический результат в зависимости от того, сколько
места реально есть на экране.

### Safe area — через react-native-safe-area-context, а не через API React Native

Встроенный в React Native `SafeAreaView` работает только на iOS.
`react-native-safe-area-context` читает системные отступы на обеих
платформах, включая Android: жестовую навигацию, кнопочную
навигационную панель и вырезы под камеру. Это единственный способ
гарантировать, что контент не перекрывается чёлкой/Dynamic Island
на iOS и навигационной панелью на Android одним и тем же кодом,
без веток `Platform.OS === "..."`.

`edges` — параметризуемый проп `Screen`, потому что экран с нижней
таб-баром не должен резервировать нижний safe-area отступ дважды
(сама таб-бар уже это делает).

### Никаких фиксированных высот

Ни один компонент фундамента не задаёт `height` в dp. `Screen`
растягивается через `flex: 1`, скролл — через `flexGrow: 1` у
`contentContainerStyle`. Это то, что делает верстку одинаково
корректной на экране высотой 568dp (iPhone SE) и 932dp (iPhone 16 Pro
Max) без единого условия по устройству — раскладка сама заполняет
доступное пространство.

### Динамическое масштабирование шрифта

React Native по умолчанию масштабирует `<Text>` в соответствии с
системными настройками (Dynamic Type на iOS, "Размер шрифта" на
Android) — `allowFontScaling` включён по умолчанию, ничего
дополнительно включать не нужно.

Проблема в другом: неограниченное масштабирование ломает компактные
элементы интерфейса (подписи вкладок таб-бара на iPhone SE при
максимальном системном размере шрифта начинают наезжать друг на
друга). Поэтому `constants/typography.ts` вводит `FONT_SCALE_LIMITS`
раздельно по роли текста:
- **`content`** (заметки в дневнике) — масштаб почти не ограничен
  (до 2×). Это то, что пользователь читает дольше всего, и здесь
  поддержка крупного шрифта важнее аккуратности верстки.
- **`ui`** (подписи вкладок, кнопки) — ограничен до 1.3×. Заметный
  прирост при включённой крупной системной типографике сохраняется,
  но верстка не ломается.

Это ограничение будет применяться через `maxFontSizeMultiplier` на
конкретных `<Text>`-компонентах, когда они появятся на следующем
этапе (`components`).

### Планшеты — базовая поддержка через ограничение ширины, а не отдельная раскладка

Полноценная планшетная раскладка (например, список + деталь рядом,
как на iPad) не входит в объём этой версии — в ТЗ значится "базовая
поддержка". Вместо отдельных экранов для планшета `Screen` и
`Container` просто ограничивают ширину контента (`MAX_CONTENT_WIDTH`,
560dp) и центрируют его. Это стандартный веб-паттерн "читаемой
колонки", он же не даёт компонентам вроде списка записей растягиваться
на всю ширину 1024dp экрана iPad, что выглядело бы разреженно и
нечитаемо.

### Готовность к смене ориентации

Сейчас `app.json` фиксирует `"orientation": "portrait"` — это
осознанное продуктовое решение (тихое, простое пространство, а не
многооконный инструмент), а не техническое ограничение. Технически
раскладка уже не привязана к portrait:

- `useDeviceMetrics` использует `useWindowDimensions`, а не
  статический `Dimensions.get()` — компонент подписывается на
  изменения размера и переотрисовывается при повороте экрана;
- классификация ширины устройства не предполагает, что высота
  всегда больше ширины (`orientation` в `DeviceMetrics` вычисляется
  из сравнения `width`/`height`, а не хардкодится);
- ни один компонент не использует фиксированные высоты, которые
  сломались бы при повороте.

Когда/если решат разрешить альбомный режим — это правка одной строки
в `app.json` (`"orientation": "default"`), без переделки раскладки.

`npx tsc --noEmit` проходит без ошибок для всего фундамента, включая
новые файлы адаптивной раскладки.
