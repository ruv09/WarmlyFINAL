# Архитектура Warmly

Этот документ описывает фундамент приложения — до того, как появится
хотя бы один экран или компонент. Задача этого этапа: структура,
которая не потребует переписывания при росте проекта.

## Структура

```
app/                     Expo Router: только файлы маршрутов, тонкие
  _layout.tsx              Корневой layout (пока без провайдеров — не нужны, см. ниже)

src/
  types/                  Общие TypeScript-типы. Ни от чего не зависит.
  constants/              Статические данные: каталог настроений, ключи
                           хранилища, токены темы, пороги роста дерева.
                           Тоже ни от чего не зависит.
  utils/                  Чистые функции (даты, генерация id).
                           Ни от чего не зависит.

  services/               Единственный слой, которому разрешено знать
                           про внешний мир: AsyncStorage, expo-notifications.
                           Экспортирует CRUD над данными и побочные эффекты.
    storage/                 StorageClient — интерфейс + AsyncStorage-реализация

  store/                  Состояние приложения (Zustand) + бизнес-правила
                           уровня приложения ("создание записи сажает дерево").
                           Импортирует services, types, constants, utils.

  hooks/                  Тонкий слой между store и экранами: подписка на
                           store, автозагрузка при монтировании, производные
                           данные (useEntriesForDate, useEntry).

  components/             Переиспользуемые UI-компоненты без бизнес-логики.
                           (пока не реализовано)
  screens/                 Композиция экранов из components + hooks.
                           (пока не реализовано)
  assets/                 Шрифты, изображения.
```

## Направление зависимостей

Это главное правило, которое держит архитектуру от превращения в кашу:

```
screens → components
screens, components → hooks
hooks → store
store → services, types, constants, utils
services → types, constants, utils
```

Зависимость идёт только "сверху вниз". `services` никогда не импортирует
`store`. `store` никогда не импортирует `hooks` или `screens`. Благодаря
этому:

- `types`, `constants`, `utils` можно использовать где угодно, они ни от
  чего не зависят и никогда не сломаются из-за изменений в UI;
- `services` можно протестировать без React вообще;
- `store` можно протестировать без рендера единого компонента;
- `components` можно верстать и показывать в Storybook/превью, не поднимая
  все стор и не мокая AsyncStorage.

## Почему именно так

**`services` — единственная точка входа к внешнему миру.**
Ни `store`, ни тем более будущие `screens`/`components` не импортируют
`AsyncStorage` или `expo-notifications` напрямую. Всё хранение данных идёт
через `StorageClient` — интерфейс с единственной сегодняшней реализацией
(`AsyncStorageClient`). Когда понадобится облачная синхронизация, нужно
будет:
1. написать `CloudStorageClient implements StorageClient`;
2. подменить его в `src/services/index.ts`.

`store`, `hooks`, будущие `screens` не изменятся ни на строчку — они
работают с сервисами, а не с конкретной технологией хранения.

**Zustand вместо React Context для `store`.**
Три причины:
- Сторы — обычные импортируемые модули, их не нужно оборачивать в
  `<Provider>` вокруг дерева компонентов. Это уменьшает связанность:
  `store` физически не привязан к тому, где в дереве компонентов
  находится экран, который его использует.
- Подписка гранулярная: компонент может подписаться на один конкретный
  кусок состояния (`useSettingsStore(s => s.settings.theme)`) и
  перерисовываться только при его изменении, а не при любом изменении
  стора целиком — важно для производительности на телефонах.
- Тестировать стор — это просто вызвать его методы и проверить
  состояние, без `render()` и `act()`.

Context остаётся оправданным выбором для вещей, которые *обязаны* быть
привязаны к дереву компонентов (например, к безопасной зоне или к теме
конкретного модального окна) — но не для глобального состояния приложения.

**`hooks` — это не то же самое, что `store`.**
`store` знает *что* такое данные и *как* их менять. `hooks` знает, *когда*
их подгружать (при монтировании экрана) и как их приготовить для конкретного
использования (например, `useEntriesForDate` фильтрует уже загруженные
записи). Если экран проверяет наличие сегодняшней записи — это делает
`hooks`, а не сам экран и не сам `store`.

Так экраны в будущем будут содержать только: вызов hooks + вёрстку.
Ничего больше.

**Бизнес-правила живут в `store`, а не в будущих `screens`.**
Правило "при создании записи попутно сажается дерево" — это правило
продукта, а не деталь конкретного экрана. Оно реализовано один раз в
`useEntriesStore.createEntry` и не будет продублировано или забыто на
другом экране, который тоже умеет создавать записи (например, если
появится создание записи из виджета или из уведомления).

**Каталог настроений — в `constants`, а не размазан по экранам.**
Добавление нового настроения — один объект в `constants/moods.ts`.

**Одно дерево = одна запись.** Стадий роста нет: дерево сразу полное.
Визуал — PNG в `assets/trees/` через `treeSpecies.ts` / `TreeIllustration`.
