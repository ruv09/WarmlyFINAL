# Навигационная архитектура

Expo Router — файловая маршрутизация: структура `app/` и есть граф
навигации, отдельного конфига роутов не существует и не нужно.

## Структура

```
app/
  _layout.tsx              Корневой Stack: (tabs) + entry/[id] + entry/new
  (tabs)/                  Группа с нижней таб-баром
    _layout.tsx              Tabs: Главная, Дневник, Лес, Календарь, Профиль
    index.tsx                 Главная
    journal.tsx                 Дневник
    forest.tsx                   Лес
    calendar.tsx                  Календарь
    profile/                      Профиль — со своим вложенным Stack
      _layout.tsx                  Stack: index + notifications
      index.tsx                     Профиль (список настроек)
      notifications.tsx              Настройки уведомлений
  entry/
    new.tsx                   Создание записи — модальная презентация
    [id].tsx                  Просмотр/редактирование записи — полноэкранный push
```

## Три уровня навигаторов и почему именно так

**1. Корневой `Stack` (`app/_layout.tsx`).**
Самый внешний уровень. Решает, что показывается на весь экран, без
таб-бара: сама группа вкладок (`(tabs)`) и экран одной записи
(`entry/[id]`). Запись открывается полноэкранно и вне вкладок
осознанно — работа с одной записью должна быть сфокусированным
действием, без таб-бара и переключения разделов рядом. Это
соответствует продуктовой философии приложения (тихое, ненавязчивое
пространство), а не только техническому удобству.

**2. `Tabs` внутри `(tabs)/_layout.tsx`.**
Пять разделов из ТЗ, порядок соответствует требованиям: Главная,
Дневник, Лес, Календарь, Профиль. Группа в скобках — `(tabs)` — это
синтаксис Expo Router для "группы маршрутов, не влияющей на URL":
`(tabs)` не появляется в пути (`/journal`, а не `/(tabs)/journal`).

**3. Вложенный `Stack` внутри вкладки `profile/`.**
Профиль — единственный раздел, у которого уже на этом этапе есть
дочерний экран (настройки уведомлений). Он реализован не как ещё
один экран корневого Stack, а как **папка** `profile/` со своим
`_layout.tsx`. Разница принципиальна:
- переход `entry/[id]` (корневой Stack) скрывает таб-бар;
- переход `profile → notifications` (вложенный Stack) таб-бар не
  трогает — человек может тапнуть на другую вкладку прямо с экрана
  настроек уведомлений и позже вернуться в профиль туда же, где был.

Это и есть ответ на требование "support nested routes": вложенность
— это не просто динамический сегмент пути, а вложенный навигатор,
который меняет то, что остаётся на экране при переходе (таб-бар),
и это осознанный, а не случайный выбор для конкретного раздела.

Тот же приём (папка + свой `_layout.tsx`) можно повторить для любой
другой вкладки, если у неё в будущем появится собственная
многошаговая навигация — остальные вкладки при этом не меняются.

## Модальные экраны

`entry/new` объявлен в корневом `Stack` с `presentation: "modal"`.
Модалка, а не push, потому что создание записи — самодостаточное,
временное действие: пользователь может закрыть его свайпом вниз, не
"уходя" из раздела приложения, в котором находился (Дневник, Главная
или Календарь — создание вызывается из разных мест, но всегда
возвращает туда же).

Любой будущий модальный экран добавляется так же: файл в `app/` +
`presentation: "modal"` в соответствующем `Stack.Screen`.

## Реестр путей (`src/constants/routes.ts`)

Файловая структура определяет маршруты, но код не должен собирать
пути строками вручную по всему приложению (`` `/entry/${id}` `` в
десяти местах — верный способ что-то сломать при переименовании
сегмента). `ROUTES` — единая точка, откуда экраны берут пути:

```ts
router.push(ROUTES.entry(entryId));
router.push(ROUTES.profileNotifications);
```

Переименование сегмента маршрута требует правки в двух местах:
файловая структура `app/` и объект `ROUTES` — не десятки мест
вызова.

## Почему навигация останется простой при росте приложения

Три конкретных правила, которые это обеспечивают:

1. **Новый раздел таб-бара** = файл в `app/(tabs)/` + одна строка
   `Tabs.Screen` в `(tabs)/_layout.tsx`. Остальные вкладки не
   меняются, ничего не пересобирается вручную.
2. **Новый дочерний экран существующего раздела** = файл в папке
   этого раздела (по образцу `profile/notifications.tsx`) + одна
   строка `Stack.Screen` в его `_layout.tsx`. Другие разделы об этом
   не узнают.
3. **Новый полноэкранный или модальный маршрут вне вкладок** = файл
   в `app/` + одна строка `Stack.Screen` в корневом `_layout.tsx`.

Ни в одном из трёх случаев не нужно трогать код, не относящийся
напрямую к новому экрану — в отличие от навигаторов, где маршруты
регистрируются в одном большом конфиге.

## Deep linking (готовность на будущее)

Expo Router строит linking-конфигурацию автоматически из файловой
структуры `app/` — путь маршрута всегда совпадает с путём файла.
`app.json` уже содержит `"scheme": "warmly"`, поэтому уже сегодня
рабочие ссылки вида:

| Ссылка                                   | Открывает                          |
|-------------------------------------------|-------------------------------------|
| `warmly:///`                              | Главная                             |
| `warmly:///journal`                       | Дневник                             |
| `warmly:///forest`                        | Лес                                  |
| `warmly:///calendar`                      | Календарь                            |
| `warmly:///profile`                       | Профиль                              |
| `warmly:///profile/notifications`         | Настройки уведомлений                |
| `warmly:///entry/new`                     | Создание записи (модалка)            |
| `warmly:///entry/<id>`                    | Конкретная запись                    |

Дополнительная настройка не требуется — это следствие файловой
маршрутизации, а не отдельная система, которую нужно поддерживать
параллельно.

Если в будущем понадобятся **universal links** (`https://warmly.app/...`
вместо `warmly://...`, чтобы ссылка из мессенджера открывала
приложение напрямую) — это добавление `associatedDomains` в `app.json`
для iOS и `intentFilters` для Android. Структура маршрутов при этом
не меняется: `https://warmly.app/entry/<id>` будет вести на тот же
`entry/[id].tsx`, что и `warmly:///entry/<id>` сегодня.

## Временные заглушки

Каждый маршрут сейчас рендерит `RouteStub` — минимальный компонент,
который лишь подтверждает, что переход по маршруту работает
(`src/components/layout/RouteStub.tsx`). Это не часть продуктового
UI и будет заменено реальными экранами (`src/screens`) на следующем
этапе — сама навигационная структура (`app/`, `_layout.tsx`,
`ROUTES`) при этом не изменится.

## Что проверено

`npx tsc --noEmit` проходит без ошибок для всей навигационной
структуры, включая типизированные параметры маршрута `entry/[id]`.
